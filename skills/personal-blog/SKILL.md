# 个人技术博客工作流

把作者实际经历过的问题、推理和取舍，写成有连续思路、技术事实可核对的文章；需要时沿用现有博客组件完成展示和发布。

## 按本次请求选择工作范围

- **起草或改稿**：优先在对话中给出文章。用户说“先写一版看看”时只交付草稿，不据此落库或发布。
- **加入博客**：读取下方站点参考，集成已选版本并实际验证页面。类别、删除占位文章、是否加入动画，以用户当次要求为准。
- **发布**：已有适用的提交/部署授权时继续完成；没有时先做好本地可审阅结果，到外部写入前再确认。技能本身不授予读取私人聊天、删除文章、推送 GitHub 或部署的权限，也不撤销会话中已经给出的授权。

不必每次都从起草重新开始，也不要求用户逐阶段批准。只做当前需要的环节。

## 将讨论写成作者自己的文章

1. 从本次相关讨论中找出：实际遇到的不适、最初做法、发现的问题、为什么改变、最后的取舍，以及还在思考的方向。涉及“已经实现”的说法，只核对支撑它的当前代码、文档或验证记录；计划、离线验证和真实上线观察分别表述。
2. 用第一人称串起因果。技术细节服务于作者为什么这么设计，避免把文章写成功能清单、工具流水账或事后堆砌的架构介绍。少用空泛总结、反复的“不是……而是……”和固定问答句式。
3. 这个作者习惯从具体体验追问机制，再提出假设逐步修正。保留这种思考过程，但不模仿聊天碎片、刻意加入口头禅或替作者虚构经历。技术问题可以展开，普通感受不必一次铺满信息。叙述中的 bot 统一用 `bot` 称呼。
4. 若用户要求从聊天归纳写作风格，优先使用现有样本；读取服务器或私人记录必须已有对应授权。按可靠账号绑定确定本人发言，区分转贴、引用与原创；不把其他群友的内容归给作者，也不把原始群聊、标识或密钥带入文章。

不要把本次 PA 文章的主题、五十条/85% 等参数套到其他项目。它们是具体设计案例，不是每篇博客的固定内容。

## 改稿保持连贯和边界

- 将已选全文作为基线。用户要求只改两处时，保留其他文字；删除要求要覆盖整段及其残留承接语。
- 合并章节时，重写过渡并消除重复，让“问题—原因—做法—结果”自然衔接，不能仅删除小标题后拼接原文。
- 按用户批注逐项处理。要求完整稿时交付整篇，不只回报改动清单。未确认的事实先校正表述，避免把润色变成错误的技术结论。

## 页面、图示与验证

涉及文件集成时读 [站点与展示参考](references/personal-page.md)。复用 `content.js` 和现有文章生成器；既有路标、阅读进度和目录无需每篇重做。

需要解释机制时再做图示。博客中的文字、卡片和容量变化，优先用原生 HTML/SVG；本次用户明确更喜欢清晰、可缩放且能自动播放的矢量动画。视频只用于用户需要视频交付的场景。保留用户选中的构图区域，不把预览界面的说明栏和控制栏全部搬入正文。

动效须实际播放验证，不能只看初始截图或语法检查。覆盖本次关键阶段与控制，例如到达阈值、压缩、摘要接续、暂停/重播；自动播放时检查可视区、离屏和减少动态效果。检查实际进度/状态，不能把收到事件误当成播放成功。

正文、目录、锚点、前后篇、分类和手机阅读做与改动相称的验证。确认文字完整，截图需实际查看。CSS/JS 更新时同步相关页面的资源版本，防止新结构配上旧缓存；不因一次内容更新重复改造全站。

## 发布交付

仅在需要发布时读 [发布参考](references/publishing.md)。它包含当前站点目录、只打包已提交静态内容的脚本、切换及回滚和线上验证要点。

结束时给出实际产物：草稿或完整修订稿、预览文件，或已验证的线上文章链接与提交。只描述做完的环节；不把 GitHub 推送、服务器切换和线上验证混成同一件事。
