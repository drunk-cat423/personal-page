让 Agent 写代码之后，我该怎么相信它写对了？

从可观察的验证结果、故障路径和独立审查出发，整理我对 Agent 代码审查的几个心智模型。

最近读了 Anthropic 的一篇文章：How the Claude Code team does code review。

读的时候，我一直在想自己使用 Agent 开发时遇到的问题：它能很快写出代码，也能详细解释自己做了什么，但我经常很难判断，这次改动到底能不能放心接受。

尤其是代码里夹杂着过多的防御性判断，以及一些价值不高的测试时，审查本身也会变成负担。

围绕这些疑问，我逐渐整理出了几个对自己有用的理解。

一、信任来自可观察的结果

文章里有一句话让我停了下来：他们现在的大部分 review，发生在 PR 创建之前。

我原来容易把 review 理解成一个固定环节：写完代码，提交 PR，再请别人检查。后来才意识到，开发者自己检查改动、运行测试、实际操作页面，以及请独立的 Agent 阅读代码，都可以提前完成。

PR 是团队协作的入口。到了这个入口时，改动应该已经带着一些可以被检查的证据。

比如修改按钮之后，能看到实际点击后的页面变化；修复存储问题之后，能检查数据最终处于什么状态。Agent 的说明可以帮助理解，但“已经完成”这句话本身，提供不了多少验证价值。

这里又能接上我此前看到的一种观点：能够明确判断的检查，尽量交给工具执行。

如果每次都让模型阅读一批结果、逐条判断是否正确，成本很高，也容易波动。把确定的判断写进脚本，之后就可以反复运行，模型主要负责调查失败和处理不确定的部分。

CLI、脚本和测试用例也可以组合起来。测试用例描述场景与预期，CLI 提供执行入口。一个脚本如果包含准备、操作和断言，它就在做测试；如果只是打印日志，那么判断工作仍然留在外面。

我想逐渐建立的，就是这种反馈：Agent 写完之后，能运行一个检查，并根据实际结果继续修正。

二、沿着故障路径选择测试

不过，有检查入口还不够。Agent 很容易写出一大堆测试，真正重要的问题却没有覆盖到。

这次讨论里，我很认可一个原则：

同一个风险，在哪一层最容易被可靠地观察，就优先在那里验证。

假设要求是“切换深色模式后，刷新仍然保持选择”。仅仅检查保存配置的函数被调用了，并不能证明这个要求成立。配置可能没有正确写入，页面也可能没有正确读取。用浏览器切换、刷新，再检查页面，能更直接地观察到结果。

如果要验证的是一个排序公式，直接给函数输入数据、检查输出，通常就足够了。

选择测试方式时，我现在会先问：这个错误是怎么发生的？测试必须保留哪些真实环节，才能让它有机会发生？

问题出在数据库事务，就需要保留真实的事务行为。把数据库完全 mock 掉，可能顺手把出错的机制也移除了。

这个角度也能帮助识别冗余测试。有些测试详细规定内部函数的调用次数和顺序，稍微调整实现就失败，但用户看到的行为并没有变化。它保护的可能只是当前写法。

我更关心的是：这条测试对应什么真实风险？如果故意引入那个错误，它能发现吗？

防御性代码也可以这样审查。一个额外判断或者异常捕获，应该说得清楚它在处理什么可达的问题。尤其需要留意那些把失败悄悄变成空结果的代码——程序看起来继续运行了，真正的问题却被藏了起来。

三、独立审查：共享事实，独立判断

实现者检查自己的代码，总会受到已有思路的影响。某个前提一旦被接受，后续实现和测试就可能一直围绕它展开。

所以，使用新上下文的审查者很有价值。但这又带来一个问题：不给上下文，它怎么知道需求？把开发过程全部交给它，它会不会也被带着走？

我比较认可的做法，是让它共享必要事实，同时保留重新判断的空间。

审查者需要原始需求、验收条件、项目约定、实际 diff 和检查结果，也需要能够继续查看相关代码。

至于实现者那段很长的“为什么这样做，以及已经考虑了哪些情况”，可以等审查者形成初步判断后，再用于解释疑问。

独立审查的价值，在于它有机会重新检查那些已经被默认接受的前提。

当然，另一个 Agent 提出的意见也需要证据。它应该指出具体位置、可触发的条件和实际影响。仅凭一个名字觉得可疑，或者泛泛地说“以后可能出问题”，还不足以要求增加代码。

“没有发现需要修复的问题”，也应该是一个正常结果。

四、审查要让问题逐步收敛

文章里有个例子让我印象很深：Agent 作者和 Agent 审查者，可能反复修改几十轮。

每一轮看起来都在认真工作，整个任务却迟迟结束不了。

文章把这个问题称为 review 必须 converge，也就是收敛。我把它理解为：随着审查推进，剩余问题应该逐渐减少，修改范围应该逐渐明确，最终走向可以接受的结果。

如果每一轮都不断增加要求、扩展范围，就值得停下来检查方向。

这在 Agent 场景下尤其重要。人可能很快略过一条价值不高的建议，Agent 却可能认真修改，再提交，再触发一轮审查。

所以，审查意见本身也需要被判断：这是实际缺陷吗？由本次改动引入吗？修复收益值得新增这些复杂度吗？是否又提出了已经讨论过的问题？

同一类错误也应该尽量一次说明白，让实现者检查相关位置。逐行、逐轮地发现同一种问题，会把一次修复拖成很多轮。

设置轮次上限的意义，是提醒我们重新检查需求、方案和审查标准。持续忙碌，并不代表持续接近完成。

五、把自动化接成有责任边界的闭环

读到这里，我之前想到的“Issue → Agent → PR”才逐渐具体起来。

现成的编码 Agent 可以承担执行者，但流程仍然需要几样基础：清楚的任务、可用的环境、项目约定、检查入口，以及明确的交付边界。

简短的项目说明，可以告诉 Agent 去哪里找资料、运行什么命令。审查说明则可以强调，这个项目最容易出现什么错误，什么样的问题值得报告。

如果某种问题反复出现，而且规则已经足够明确，就可以考虑把它做成 lint 或脚本。需要判断的部分留给人和模型，重复检查交给工具。

人的注意力则应该随风险分配。修改文案和修改权限控制，值得投入不同的审查力度。判断依据来自实际改动及其影响。

Agent 可以协助检查，但需要人承担的判断和责任，仍然需要有人接住。一次批准也只覆盖当时看到的代码，后续新增的修改需要重新确认。

对我自己的项目来说，可以先从一个小闭环开始：写清需求和验收，给 Agent 一个能运行的检查入口，再让独立上下文的审查者检查改动。

然后观察它究竟发现了多少真实问题，又制造了多少无效修改。

我希望逐渐掌握的，是判断哪些结果值得相信，哪些问题需要继续追问，以及什么时候，这次改动已经足够好了。
